**Which iteration is current.** The 481–486 sections are the final design: they carry the KW Habilitation logo header, the *Your Events / All Events* toggle, a *View Details* → *Event Details* page, and the superadmin *Account Management / Event Management* switch. The 404:* section is an earlier pass in a different chrome ("ADMINISTRATIVE ACCESS / Sophia L." header, per-card action icons, the older create form). Six 404:* frames are retired outright; five others are kept in `08-admin-posted-events` because they are the **only** frames that show a state the newer iteration never redrew (expanded filters, delete confirmation, and the three toasts). Treat their *chrome* as stale and their *interaction* as current.

**A finding about the code that changes how to read everything below.** CLAUDE.md still describes `/host/*` as "sidebar (Programs / Admins / Members) … dense, squared-off, table-first". That is no longer what `/host/events` is. `app/host/events/page.tsx:24` mounts `AdminShell … bare`, which returns the children without the sidebar frame (`AdminShell.tsx:116`), and the page renders `ConsoleHeader` pill-tabs plus a filter accordion beside a column of `PostedEventCard`s (`components/host/PostedEvents.tsx:241`). The admins and users pages are also `bare` (`admins/page.tsx:36`, `users/page.tsx:33`) but still lay their rows out with `TableCard`. So the "cards vs table" conflict the brief asked me to watch for has mostly already been decided in the card direction for the programs list; what remains is the account table (design and code agree it is a table) and CLAUDE.md needing an update.

## New backend work implied

1. **Important Links (×3).** New `events.links` (JSONB/`ARRAY(Text)`, migration) or three nullable columns; expose on `EventOut`, accept on create/update. Decide how it relates to `registration_url` (below) before adding it — otherwise there will be two places to put "the sign-up page".
2. **Emailed organizer invites.** `POST /invites` (`backend/app/api/routes/invites.py:44`) returns a token the superadmin pastes into a message. The design's "Send Email" needs the route to send via `app/core/mail.py` with `FRONTEND_ORIGIN` for the link — same infrastructure and same "unset SMTP → logged, not sent" caveat as password reset. The design's invite form has **no organization field**, but `HostInvite` requires one (`admins/page.tsx:391-394`); either the form keeps the field or the invitee names the agency on accept.
3. **Optional:** `host_id` (or `mine=true`) filter on `GET /events` (`events.py:111-117`) so *Your Events* doesn't page the whole calendar client-side; `q` already searches title only (`events.py:130`) while the console searches title+description+location+host client-side (`PostedEvents.tsx:79-85`) — leave as is or widen `q`.
4. **Optional:** server-side 1000-char cap on `description`.
5. **Nothing needed** for: attendee count (`saved_count` already on `EventOut`), end time (`ends_at` already accepted), un-publish (archive route exists, plus `restore`), event details page (`GET /events/{id}` exists), share (copy link, no tracking drawn).
6. **Flag, don't plan:** "20 Attendees" on every admin card is a per-event stat surfaced to the NPO — **M-1**, recorded out of MVP scope. The number is already computed; the decision is whether to show it.

## Conflicts / decisions Jesse must make

1. **Activity Type is gone from the v2 form but present in the v2 filter.** Keep the category picker regardless of the design (CLAUDE.md: every live event carries a category; matching is string-equality). Ask the designer where it goes, don't remove it.
2. **Important Links vs `registration_mode`/`registration_url` (§3.1).** Three untyped links cannot tell the member app which one is the registration link, which is the field the four registration states hang off. Options: (a) keep Posting link as the typed registration URL and add up to two "more links"; (b) make Link 1 the registration link by convention (fragile). Recommend (a).
3. **Form scope: v2 is much thinner than the code.** Pricing detail, recurrence, capacity, ages, notes, access tags, Youth all vanish. Each has a register row depending on it (R-6, D-6, D-8, N-1, the 273-occurrence import). Likely the design is showing the common case, not deleting features — but it needs saying out loud before anyone "matches the Figma".
4. **Required markers.** v2 stars four fields; N-1 and the code require image, description and category too. Keep the code's set; add the stars back to the design.
5. **Multi-person organizations (486:14826).** Name / Email / Non-Profit with several people per agency contradicts §3.5 and A-6 (one shared login per agency, revisit only if an agency asks). Either the table's "Name" column shows the organization (today's behaviour) or §3.5 is being reopened. Same question hits the header ("Sophia L. / Admin" vs today's organization name, `ConsoleHeader.tsx:118`).
6. **Trash icon on an organizer row.** Removing an organizer archives the account **and every program it posted** (CLAUDE.md invariant). Today's Remove modal warns with the program count (`HostWithCountsOut.event_count`); a bare trash icon with no confirm would lose that. Keep a confirmation.
7. **Superadmin promotion.** v2 has no Access column and no "Make superadmin"; the code has both (`admins/page.tsx:189-203`). Dropping it leaves KW Hab unable to add a second superadmin without the API. Keep it.
8. **Delete vs Un-publish wording.** v1 says delete; v2 says Un-publish; the API archives. Standardise on **Un-publish** (modal, toast, `DeleteConfirmModal.tsx`, `ConfirmDelete`) — it is the one word that is true. N-5's "superadmin-only" wording is what's stale, not the code (owners may retire their own unsaved program).
9. **Where share and print live.** v1 had share/print/edit/delete icons per card (all built, `PostedEvents.tsx:373-403`); v2 cards have only View Details, and the details page has only Edit / Un-publish. N-7 requires copy-link on every row. Either keep the row icons or add Share (and Print) to the details page.
10. **Edit as a page vs modal.** v2 draws Edit Event Details as a page with a back arrow; code opens a modal over the list. Either satisfies N-2 because both use `EventForm`. A page gives the details view a natural sibling route (`/host/events/[id]`, `/host/events/[id]/edit`); recommend the page if the details view is built.
11. **Publish toast without Undo.** v2's toast (484:13832) is a plain confirmation; code's has Undo (N-6). Keep Undo, take the styling.
12. **CLAUDE.md is stale about the console.** "Sidebar Programs / Admins / Members" and "table-first" no longer describe `/host/events`; `AdminShell`'s Frame is now only reached by the superadmin-refusal screen (`AdminShell.tsx:102-114`). Update the doc rather than "restore" the sidebar — the v2 design and the code agree on the card list with header tabs.
13. **Two superadmin destinations vs three.** Design: Account Management / Event Management. Code: Events / Users / Organizations. Users (member key reset, A-3) is not drawn anywhere in the design; keep it.
14. **Design copy bugs to not ship:** 481:6170 subtitle "Login to start saving events."; 404:26301 deleted-toast reads "posted"; 483:12966 name placeholder "Enter your first name".
