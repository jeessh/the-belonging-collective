## New backend work implied

1. **Share event by email** (404:28717, and "Share list" on 431:13693 / 446:13000): `POST /events/{id}/share` and `POST /users/me/events/share` taking a recipient address; send with `backend/app/core/mail.py:26 send()`; guard with `core/rate_limit.py enforce()` per member and per IP (an anonymous "send this to any address" endpoint is a spam relay otherwise); the body needs the event page URL plus a calendar attachment. Requires `SMTP_*` configured in production (today unset means the mail is only logged).
2. **Calendar export** ("Google Calendar" on every saved-events frame and the sidebar; the share mail promises "a link to add the event to their calendar"): a Google Calendar *template URL* is pure frontend; an `.ics` for one event or the whole saved list is best served by the API (`GET /events/{id}.ics`, `GET /users/me/events.ics`) so the share mail and the button use the same file. No schema change — `starts_at`, `ends_at`, `location`, `description` suffice. Register R-8.
3. **Nothing else.** Attendee counts (`saved_count`), tags (`is_free` / `requires_signup` / `is_virtual`), relative dates, time ranges, Undo-after-unsave (`POST /attend` re-saves a `removed` row, `attendance.py:49–76`), Print list (`@media print` already exists in `globals.css:44`), and the multi-select filters can all be done in the frontend against the current `EventOut`. "See on Map" as a maps search link is frontend-only; a real map needs coordinates (D-4, out of scope here).

## Conflicts / open questions

- **Filters vs "sorts, never filters".** The chip row is captioned "SORT EVENTS BY 0 FILTERS" but the `Filter Dropdown Options` component is a multi-select checkbox list (Non-Profit / Price / Registration / Event Type / Activity Type). CLAUDE.md allows only the member's *explicit* cost/organization filters to remove cards; §D-1 keeps interest as a sort. The chips FREE / SPORTS / FOOD / SOCIAL / ART / GAMES / INFORMATIVE mix a cost flag with topics that are **not in `CATEGORIES`** (`lib/categories.ts:16–28` has Sports and Games but no Food / Art / Informative — Cooking, Arts & Crafts, Education are the nearest). Needs a decision: explicit chips as filters (allowed) with the canonical vocabulary, or as sort boosts. Either way the chip labels must come from `CATEGORIES` / the future categories table (§3.6), not a hand-typed list.
- **Copy (§3.3).** "Login to start saving events." (429:13451), "Create an account to save events to your page and calendar" (Modal Card), "We will send a link to add the event to their calendar." (Share modal) are explanations, not labels. The last one at least carries a promise the backend must keep (see item 2 above).
- **Saved sidebar while signed out.** 435:10236 and 393:7684 show four saved thumbnails in the rail under a "Not Logged In" header. Saving requires an account (§3.7, `EventsView.tsx:345`); either the rail is signed-in-only or the mock is a placeholder. Also the design shows no un-save control on `Saved Event Card`; today the bookmark on `GridCard` is the *only* un-save affordance, and the unsave toast (431:13693) implies one exists somewhere.
- **Drop direction.** The sidebar's dashed "Saved Events go Here" reads as a drop target to the **left**; today's gesture is drag **down** into `SaveZone` (`DROP_THRESHOLD`, `EventsView.tsx:68`) and drag **up** opens the saved overlay. The keyboard / voice / head-dwell routes (X-1) are all wired to the current gesture; changing direction touches every one of them.
- **Sidebar as persistent chrome** (both card and list frames) replaces today's full-screen `SavedEvents` overlay and the bottom `SaveZone`. That is a layout change to the carousel's height budget (`FeedParts.tsx` comments explain why the card is height-led).
- **"Continue as guest" and the guest toast** (Modal Card, Toast variant c) presume a guest *mode*; §3.7 already makes browsing open and only gates save / register, so these are either redundant or mean something new (session-only saves?). Clarify.
- **Two "Community Member" role cards** in Modal Card / Frame 626: if one becomes "Non-profit", it re-opens a host signup door §3.2 closed. Flag to whoever owns the auth slice.
- **Share by email from a member with no email** (R-7): the sender has no address on file, so the mail has to go out from `MAIL_FROM` with, at most, the member's first name. Recipient consent / abuse is the open question, not the schema.
- **"20 Attendees" / "20 People Going"** exposes `saved_count` publicly. §M-1 put per-event counts out of MVP scope for the *NPO console*; showing them to members is a different question (privacy of a small support-group's headcount) and should be decided, not inherited from the mock.
- **Pink "Save Event"** on 399:11385 has no matching component variant; confirm whether it is the saved/un-save state, an error state, or a stray fill.
- **Accessibility scope (§3.4)**: nothing on these frames asks for text-size / contrast toggles; the "Accessibility Tools" dropdown matches the existing menu. No conflict. The list rows and the sidebar rail are new custom interaction surfaces that will need the same keyboard / announcement care the carousel has (X-4, X-8).
- **Backdrops are stale.** The three More Information frames sit on the retired day-sectioned grid (`Old Grid Card` layers); only the modal on top is current.
